跑通 vLLM 只要一条命令。但如果就此上线，你会在第一次压测时发现吞吐只有预期的三分之一，而且不知道问题出在哪。

这篇只做一件事：把「能跑」和「跑稳」之间的差距拆开。读完你应该能在自己的机器上复现一组数字，并且知道这些数字为什么是这个量级。

## 一、跑通：一条命令和三个必填参数

最简启动大概是这样。但下面这三行注释才是重点——它们决定了你后面测出来的所有数字有没有意义。

```bash
# 这三个参数决定后面所有数字是否有意义
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.9 \
  --max-num-seqs 32
```

先把环境写清楚，否则所有结论都不可迁移：**GPU 型号、驱动版本、CUDA 版本、vLLM 版本、模型量化方式**。少一项，别人复现不出来，就会认为你在编。

## 二、三个参数各自牺牲什么

调大 `max_num_seqs`，吞吐会上去，但 TTFT 会变差；调大 `max_model_len` 能支持更长上下文，可显存被 KV cache 吃掉之后，并发就上不去。

这三个参数不是独立的——它们在同一条显存预算上互相挤。理解这一点，比记住任何一组推荐值都有用。

> 没有免费的并发。你调高的每一个上限，都在别处扣掉一部分余量——而那一部分通常不会立刻显现。

所以「最优配置」这个问题本身是错的。正确的问法是：**我的场景更在意首字延迟，还是更在意单位时间吞吐？** 答案不同，配置就不同，没有通用解。

## 三、第一次压测要看四个数

不要只看 tokens/s。四个数一起看，才知道你的吞吐是用什么换来的：

- **TTFT**（Time To First Token）——用户点下去到看见第一个字的时间，决定「感觉快不快」。
- **TPOT**（Time Per Output Token）——后续每个 token 的间隔，决定「读起来顺不顺」。
- **吞吐**——单位时间产出的 token 总数，决定「一张卡能服务多少人」。
- **显存峰值**——决定你还有多少余量加并发，或者会不会在高峰期 OOM。

只看一个数，一定会得出错误结论。吞吐翻倍但 TTFT 从 300ms 涨到 2s，那是退步，不是进步。

## 四、常见假象：吞吐涨了，延迟也涨了

这是最容易骗过自己的一种情况：把并发堆上去，吞吐曲线很漂亮，但每个用户的等待时间也在同步变长。

判断方法很简单——**把吞吐和 TTFT 画在同一张图上**。如果两条线同向上升，你并没有变快，只是把队列排得更长了。

## 五、本篇的边界

这篇只到「能稳定跑」。下面几件事本篇没有涉及，但会影响你的最终表现：调度策略与连续批处理的内核实现（第 2 篇）、并发与延迟的定量取舍（第 3 篇）、以及什么情况下这套方案根本不该用（第 5 篇）。

如果你的场景是**单用户、低频、对延迟不敏感**，那 vLLM 的价值会大打折扣——直接用 transformers 反而更省心。判断标准不是「它更快」，而是「你有没有足够的并发把它的优势摊开」。
